# 0004: Canonical message tree, generation candidates, and source identity

Date: 2026-09-08  
Status: **accepted for plan 02 contracts; implemented and validated in core**

This resolves the relationships required by [plan 02](../plans/02_define_canonical_history.md). The implementation lives in `@quixi/core/model` and `@quixi/core/contracts`, with [worked fixtures and source evidence](../../tests/fixtures/canonical/README.md). The A1 backend feasibility gate permits these contracts to proceed while the remaining platform qualification stays tracked in plan 01. A1 proof tables remain disposable developer data; plan 03 owns the canonical SQL schema and durable implementation.

## Relationships and one copy of content

Use the `Message.parentId` tree as the sole continuation topology. Every message belongs to one thread. A null parent attaches to that thread's implicit root; multiple roots allow an edited first message. Parent links never cross threads, form cycles, or change after insertion. Roles are `system`, `user`, `assistant`, and `tool`; preserve unfamiliar source roles in raw provenance with a warning rather than guessing their meaning. [Product §§16–20](../product.md#16-canonical-conversation-model)

Each `Generation` is one candidate attempt, anchored by `parentMessageId`. It has one reserved assistant `outputMessageId`; that message has the reciprocal `generationId` and the same `parentId`. A failed attempt can therefore retain an empty or partial output and its status without inventing successful text. Regeneration creates a new Generation and sibling assistant message with fresh IDs. Simultaneous candidates follow the same rule; if one provider request produces several candidates, retain a shared opaque request reference in metadata while assigning distinct Generation IDs. The candidate's provider/account/model live on Generation, not on every message. [Product §18](../product.md#18-generation)

`ContentPart` has one canonical owning message, stable ID, order, kind, and structured payload. `ContentPart.messageId` and `order` are authoritative; `Message.partCount` records their count without carrying an unbounded ID manifest. `readMessageParts` provides ordered cursor paging. `Message.parts` in the conceptual spec is a read-only projection of these records. `Generation.parts` in the conceptual product model is a read-only view of its output message's parts; it is not a second writable store. This prevents text and attachment copies from diverging. The initial kinds are exactly Text, Image, File, Audio, Citation, ToolCall, ToolResult, ReasoningMetadata, StructuredData, ProviderArtifact, and Note. [Product §19](../product.md#19-content-parts)

Text and Note each contain exactly one bounded inline string (at most 16,384 UTF-16 code units) or a SHA256/byte-length/UTF-8 blob reference. Long imported text uses verified `canonical_text` blob transfer; bytes must pass actual UTF-8 validation, not merely a declared encoding. Streaming adapters can use `inlineTextSegments` to create bounded new Text parts without splitting surrogate pairs. They retain allocated IDs on retries. Previously sealed parts never become a writable consolidation target. Large raw structured/tool payloads are retained via raw source/artifact references with compatibility facts; importer adaptation belongs to plan 04.

Native tool calls are ordered ToolCall parts on the assistant output. Executed tool results become child messages with role `tool` and ToolResult parts pointing to the canonical call-part ID. Several results form a deterministic chain in stored execution/source order; the next model attempt starts after the last result. Execution order must not be inferred from timestamps alone. An imported source can instead put call and result blocks inside one message: retain that grouping and link the parts without manufacturing separate conversation turns. A result refers to an earlier call in the same message or an ancestor. Unresolved provider call IDs are explicit unresolved references with warnings, never guessed cross-thread links.

An imported assistant message may have `generationId: null`. A message export does not necessarily establish attempt boundaries, per-message provider/model, request parameters, token counts, or completion state. Preserve available text and provenance without synthesizing a successful Generation. When the source does establish those facts, create the linked Generation. A thread-level model label alone is not evidence of the model used for every historical response.

## Identity, time, edits, and active path

Quixi primary IDs are opaque lowercase UUIDv4 strings allocated when a logical action is first created and injected into pure core functions; core does not call DOM, Tauri, SQL, provider, or inference APIs. UUID format validation uses only pure string checks. Native IDs remain stable through archive round trips and sync. Provider-native identifiers are separate source identities scoped by provider, source account/organization, source thread, entity kind, and native ID. `sourceContainerKey` scopes a native ID even when the source omits a native thread ID: use the known thread ID, or a declared source fingerprint plus entry locator. Keep `sourceThreadId` null when absent. Titles, array position alone, and display names are never identity. Reimport resolves that scoped identity to an existing Quixi ID. When provider identity is missing, importers supply a versioned fingerprint and confidence; they must not silently merge on title. [Product §26](../product.md#26-import-provenance), [§25](../product.md#25-incremental-import)

Canonical times use UTC Unix milliseconds as finite safe integers, with `null` for unknown source time. `recordedAt` is the actual local ingestion/commit time; it must not impersonate an unknown `createdAt`. Preserve original timestamps, precision, and source semantics in raw provenance. Parentage, candidate membership, and source ordering are explicit relationships, never derived by sorting times. Monetary values use decimal strings plus currency and estimated/reported provenance; token counts are nonnegative safe integers or null, never invented zeroes.

Completed messages, parentage, roles, ordered parts, and finished generation results are immutable. Editing a message creates a fresh sibling at the original parent, with `editedFromMessageId` referencing the old message. For an edited generated response, the new assistant message is a user-authored revision with no generation backlink; it does not claim that the model generated the edit. Descendants stay attached to the old node. Regenerating or continuing the edit creates new descendants. Editing a system prompt similarly creates a new context version rather than rewriting prompts used by existing attempts. [Product §20](../product.md#20-branching)

`Thread` retains `workspaceId`, creation time, initial `systemPrompt`, `preferredRoute`, and optional import-source reference. Context changes create immutable versioned `ContextSnapshot` records; each Generation pins the context-snapshot ID used for that attempt. Prior attempts retain their original prompt/routing context. `ThreadState` holds title, tags, pinned, archived, routing profile, active context snapshot, and `activeLeafMessageId`. The active leaf is the selected **display-path endpoint**; it may have other retained descendants in the full tree. Resolve its ancestor chain to produce the displayed path. An empty thread has null active leaf; a non-null selection must identify a visible message in that thread. Creation of a sibling candidate never changes the active path implicitly: selection is an explicit `SetActiveBranch` mutation. A generation started from a selection records that exact parent, even if the user changes selection while it streams. [Product §16](../product.md#16-canonical-conversation-model)

Mutable generation state has one lifecycle: `streaming` → one of `complete`, `stopped`, `failed`, `cancelled`, `partial`. Terminal states are sealed. Imported known terminal attempts may be created already sealed. Streaming checkpoints append new parts or append text to the current unfinished part; they cannot overwrite a sealed part or prior prefix. Persist each checkpoint with its own monotonic sequence and atomic sync operation; in-memory network token events are not falsely described as committed history. Finalization seals output and appends `CompleteGeneration` with the terminal status. Stopped, failed, and cancelled attempts retain text received before termination.

Logical deletion is a separate tombstone mutation, not an edit to immutable content. `TombstoneThread` hides its history; `TombstoneBranch` records a bounded root scope whose descendants are hidden, and moves a deleted active selection to its closest visible ancestor in the same transaction. Tombstones do not enumerate descendant IDs. Local mutations cannot grow deleted threads/subtrees; SQL resolves scope without a whole-thread payload. Do not physically delete an ancestor while retaining dangling descendants. The later storage/archive and sync plans own physical purge, retained-operation compaction, and multi-device deletion reconciliation; this contract does not promise permanent retention after a user explicitly requests erasure.

## Provenance, unsupported content, attachments, and search

Every imported entity can link to an `ImportSource` observation containing provider, method, source thread/URL, importer/version, optional source-format version, fingerprint, and actual import time. Keep provider identity separate from normalization observations so a later importer can add an observation without changing the entity's Quixi ID. Store exact retained source bytes under a SHA256-addressed raw-object reference plus an entry locator (e.g. JSON Pointer). An absent original bundle is explicit; a JSON object re-serialized by Quixi must not be claimed as the original byte stream. [Product §21](../product.md#21-raw-provider-preservation), [§26](../product.md#26-import-provenance)

An unsupported source block becomes a ProviderArtifact with its provider kind and raw locator; it is not discarded or automatically treated as transferable text. Compatibility metadata records unsupported, redacted, truncated, and inferred-order facts independently. `ReasoningMetadata` can record that source reasoning was redacted; never fabricate missing reasoning text. ThreadEvent retains ProviderSwitch, AutomaticFallback, ContextCompaction, ImportWarning, Migration, and UserNote details and optional related message/generation IDs. [Product §§19–22](../product.md#19-content-parts)

Attachments have a stable logical reference with display metadata and source file identity. Availability is explicit (`available`, `missing`, `unavailable`); only available local bytes have a verified SHA256/content-addressed blob reference. Missing bytes retain filename, MIME/type, source size/hash when provided, and an ImportWarning. A provider MD5 is source metadata, not a Quixi verified blob SHA256. Resolving a missing attachment appends `ResolveAttachment` and its sync operation, retaining previous provenance. Blob staging/fs writes precede an atomic SQLite reference commit; orphan staging is recoverable. SQLite cannot atomically commit OPFS file writes, and this decision must not imply it can.

`Document` retains canonical ID, workspace ID, attachment ID, title, source creation/local recording times, and optional import-source ID. `RegisterDocument` and `SetDocumentTitle` produce sync operations. The attachment owns byte availability and verified blob identity; a missing file does not erase the document metadata. Workspace IDs are externally scoped identities; workspace membership/policy is not invented as a conversation record here. Parsed text, page/OCR output, extraction status and search indexes are derived, versioned records rebuilt from source bytes. Plan 03 stores metadata and publication; later document plans implement extraction and its cache lifecycle.

SearchChunk refers to message/document/OCR/code/tool-output sources and, when useful, exact part IDs and source ranges. It records chunker/version, source content digest, chunk index, text/context prefix, and optional tokenizer/range metadata. Embedding model and state describe derived indexing only. Chunk IDs may be versioned deterministic derivations and must not become canonical content identity. FTS, vectors, compressed indexes, and ranking caches rebuild locally and do not generate canonical sync operations. [Product §47](../product.md#47-searchchunk), [§97](../product.md#97-derived-data-and-sync)

## Atomic operations and validation contract

Storage accepts serializable domain commands with an operation ID assigned by the caller **before dispatch**. The worker may allocate it only when creating a new logical action on behalf of a caller; retries and unknown-outcome reconciliation must retain the original ID. It commits all affected canonical records plus the corresponding `sync_ops` record in one SQLite transaction. Repeating a previously committed operation ID returns its recorded result or a payload-conflict error; it never repeats the mutation. A retry with a new operation ID is a new action. This is the local contract, not a Cloud wire/encryption design. [Product §96](../product.md#96-synchronization-operations)

| Command or mutation | Same-transaction coverage |
| --- | --- |
| CreateThread | Thread, initial ThreadState and ContextSnapshot, creation sync op |
| CreateMessage / EditMessage | New message and parts, provenance/source identity references, edit link when applicable, explicit optional active-path change and its op |
| CreateGeneration | Generation, reserved output message, initial parts, requested active-path change and their operations |
| AppendGenerationOutput | Sequence-checked durable append/checkpoint and sync op; no silent overwrite |
| CompleteGeneration | Terminal state, final usage/cost/raw-response reference, output sealing, completion sync op |
| CreateThreadEvent | Event and sync op |
| SetTitle/Tags/Pinned/Archived/ActiveBranch/RoutingProfile | ThreadState change plus corresponding sync op |
| RegisterImportSource / AttachProvenance | Source observation/raw reference/scoped provider identity mapping and sync op |
| RegisterAttachment / RegisterDocument / SetDocumentTitle | Logical attachment/document metadata or document title plus its sync op |
| AttachContent / ResolveAttachment | AttachContent only adds to an unsealed message; a new attachment on sealed history requires an edit/revision. ResolveAttachment updates the stable attachment reference's availability/provenance, never sealed message parts. Both commit verified staged blob references and sync ops. |
| CreateContextSnapshot | New immutable system-prompt/routing context version, optional state selection, and sync ops; prior attempts keep their snapshot IDs |
| TombstoneThread / TombstoneBranch | Tombstones, affected active state, and sync ops |

An import commits a logical thread in bounded batches only when its plan explicitly supports recoverable multi-transaction staging; the final visible graph cannot contain half-resolved references. Raw/blob writes and network transport do not run inside the SQLite transaction. Plan 03 selects tables and migration layout; plan 25 selects transport, encryption, convergence, and operation-retention rules.

Core validators must reject duplicate IDs, dangling/cross-thread/cyclic parents, inconsistent generation/output links, duplicate part order, invalid times, invalid terminal transitions, edits to a different parent/role, active selection outside the thread, present attachments without verified blob references, and resolved tool links outside ancestry/order. Missing source references are represented as explicitly unresolved import facts, not silently accepted broken canonical foreign keys. Errors carry stable codes, entity/path, and explanation; persistence/host error mapping stays outside pure model validation.

`StorageClient` commands/results, HostClient capabilities, provider-native import bundles, bounded transfer acknowledgments, progress, and cancellation remain separate `core/contracts` exports. SQL, Worker objects, filesystem handles, credential values, and inference handles cannot appear in serializable domain payloads. Caller-assigned request IDs make cancellation addressable. Logical operation IDs survive transport retries and unknown outcomes; `operationStatus: not_found` is only an observation while the original operation may still be in flight. Cancellation distinguishes not-dispatched from unknown write outcome; committed writes are not undone merely because a caller stopped waiting.

Control requests and replies are limited to 1 MiB by an incremental UTF-8 JSON preflight, avoiding a complete serialization allocation before rejecting oversized values. Pages carry item/byte budgets. Binary transfers use at most four unacknowledged 1 MiB chunks, sequenced offsets and explicit final markers, with at most 64 pending control requests. Chunk acknowledgments apply backpressure; final completion waits for all acknowledgments. Cancellation and progress contain serializable IDs and values, never AbortSignal/Worker objects.

Native attachments do not require an import bundle. `beginBlobTransfer` declares purpose/optional expected size and hash; finish checks the received bytes against final required size/hash and returns verified staging. `MutationBatch.stagedBlobIds` contains the begin-returned transfer IDs authorized for publication. Storage must publish only hashes backed by verified staging or existing published blobs, in the same SQL transaction as canonical references and sync ops. File writes themselves precede that transaction. Read transfers expose published hashes; discard is idempotent and cannot erase published referenced blobs. Crash recovery and physical orphan cleanup belong to plan 03.

HostClient includes explicit capability permission/reason and transport privacy/relay identity, registered provider/account/destination/transport bindings for credentials and HTTP, bounded timeout declarations, and host-owned OAuth configuration/state/PKCE. Callers supply a registered configuration ID rather than authorization URL/state. Outbound host bytes have begin/finish/release lifecycle; selected files have release. Hosts enforce these contracts in later plans. After provider dispatch, cancellation reports that external effects may have occurred; it cannot guarantee no computation or billing.

The local sync log exposes monotonically increasing sequence independently of operation UUID identity. `readSyncOperations({afterSequence,page})` pins a paging cursor to a captured high-water sequence; later commits are consumed from the last delivered sequence. This is bounded local inspection, not the Cloud transport protocol.

## Validation and remaining evidence

- After plan 03 scale review, the bounded root-scope tombstone, partCount/ordered paging, blob-backed Text/Note and monotonic sync-inspection corrections are included in the accepted contracts. The reviewed message/output ownership, imported unknown Generation facts, explicit active endpoint, immutable edits/context, append/seal lifecycle, tombstones and operation identity are implemented as pure model/contract rules. Tests exercise all 23 mutation kinds and their expected write effects, preserving the original input on successful and failed previews.
- On 2026-09-08, `npm run typecheck --workspace @quixi/core`, `npm run typecheck:tests --workspace @quixi/core`, and `npm test --workspace @quixi/core` passed: 37 tests, no failures or skips. The source tsconfig admits ES2022 only and no ambient Node/DOM types. Fixture tests verify raw-byte digests/lengths, provenance pointers, branch outcomes, malformed relationships and a 10,000-message chain, bounded long-text segmentation, exact inline/blob exclusivity and sequence-based sync inspection. See the [fixture guide](../../tests/fixtures/canonical/README.md) for reproducible commands and exact coverage.
- **Consumer-export compatibility remains unverified:** the original ChatGPT export-shaped fixture follows the maintained LangChain loader's represented subset; the original Claude fixture follows documented Compliance API fields and deliberately adds an unknown block. Neither is a captured personal export or an official complete/current personal-export schema. The representative fixture requirement is satisfied; actual importer compatibility must be established in plan 04.
- **Durability is separately evidenced in plan 03:** pure transition previews and effect coverage do not establish SQL atomicity, persisted replay/idempotency, OPFS publication, migrations or crash recovery. [ADR 0006](./0006-canonical-persistence.md) records the private SQL implementation and its tests, with complete-thread/many-part staged import publication still outstanding. Host interfaces likewise do not implement capability or destination enforcement.
- **Deferred to later plans:** Cloud wire payload/encryption, merge clocks, multi-device conflict/deletion reconciliation, retention/purge policy and physical blob garbage collection. Local atomic sync-operation coverage is required even when Cloud is disabled.
