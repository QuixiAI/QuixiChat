# 0006: Bounded canonical SQLite persistence

Date: 2026-09-08  
Status: **implemented canonical repository and staged import publication; production worker/blob integration has separate browser acceptance**

[Plan 03](../plans/03_build_storage_repositories.md) persists the [canonical contracts](./0004-canonical-history.md) in the same pinned SQLite WASM distribution used by every host. Only the owning Storage Worker receives a SQLite handle. Node acceptance uses that actual WASM build with Emscripten's memory filesystem; it establishes SQL behavior, not OPFS or process durability.

## Records, relationships and migrations

`quixi_records` contains a collection discriminator, Quixi ID and bounded canonical JSON, with stored/generated indexed relationship columns. This preserves the shared shape while giving message parentage, thread membership, part ownership and part order indexed SQL access. A partial unique index enforces global canonical identity while allowing ThreadState to use its Thread's ID. `quixi_edges` captures references with deferred foreign keys to collection/ID pairs. Message/output, part order and scoped provider identity also have dedicated unique indexes. SQL triggers protect immutable records, sealed messages, append-only unfinished text, terminal generation identity, revision increments and published attachment bytes.

The repository reuses core's `validateEntityShape` on one bounded record, then checks affected relationships through indexed probes and SQL traversal. It never constructs a whole-thread or whole-archive CanonicalHistory. Initial part counts are checked against SQL aggregates; later append commands extend the validated count and consecutive order under the same transaction. New parent/edit targets must exist before insertion, and there is no reparent mutation, preventing creation of cycles. Tool results must resolve to preceding same-message or ancestor calls.

Ten ordered migrations create canonical records/edges/operations, relational uniqueness and immutability guards, the durable blob catalog/transfer tables, hidden normalized import groups and their replay/transfer bookkeeping, durable importer work/UUID/checkpoint controls, local generation producer fences, bounded-view metadata/indexes, and the [streaming text/provenance append rule](./0013-streaming-text-and-provenance.md). Migration 9 adds the committed [managed archive access barrier](./0012-archive-selection.md) without rewriting user history. Migration 10 adds [durable local operation claims](./0015-durable-derived-operation-claims.md), independent of repairable extraction/search data and excluded from portable history. The migration ledger records version, name and SHA256 of canonical-serialized migration SQL; startup rejects changed, missing or future history. Each upgrade and ledger entry share a transaction. The ledger is independent of the disposable A1 proof's `user_version`. An upgrade failure rolls back, preserves prior data and reports recovery guidance; no automatic wipe or downgrade occurs. Portable/open exports, restore validation and managed activation have separate browser acceptance; complete host/scale recovery qualification remains open.

## Atomic operations, replay and source identities

Every one of the 24 canonical mutation kinds is implemented. The repository owns a synchronous `BEGIN IMMEDIATE` transaction; the worker serializes requests and performs no awaited I/O inside it. Each mutation's actual write set becomes its `sync_ops.affects`, and record writes, reference edges, operation payload/result and transaction replay result commit together. A thrown validation/blob/SQL error or injected failure rolls back the entire batch. Derived search/index data does not produce canonical sync operations.

Operation IDs and transaction IDs retain their original payload identity. A SHA256 of canonical JSON detects reused IDs with different arguments. Repeating the exact transaction returns its recorded result. Reusing already committed operations in a new transaction returns `already_committed`, and a full replay bypasses stale optimistic revisions. Mixed replay/new work still checks the requested base revisions before new mutations. `committedTransaction(batch)` provides a read-only preflight before costly blob publication; `commit` repeats the check under its SQL transaction.

Scoped source-ID resolution is available before an importer constructs mutations. A unique SQL index over provider, account scope, optional native thread, source container key, entity kind and native ID rejects overlapping conflicting mappings. Importers retain the resolved Quixi ID and add provenance separately; they must not blindly insert another identity row for the same source key. Constraint failure rolls back any associated observation writes.

Sync rows have a monotonically increasing local INTEGER sequence separate from their UUID. `readSyncOperations` returns bounded sequence-ordered pages, pins cursors to a captured high-water sequence and exposes the last delivered sequence for later polling. UUID lexical ordering cannot substitute for commit position. This local inspection format does not decide Cloud wire encoding, encryption, convergence or operation retention.

## Working-set bounds without an archive-size limit

Control messages are at most 1 MiB, batches at most 128 mutations, each stored metadata/part record at most 256 KiB and pages at most 1,000,000 bytes inside the response envelope. The repository fetches one record at a time; using OO API `resultRows` with a large page limit would otherwise allocate item-count × maximum-record-size. `readEntities` uses ID keyset pagination; `readMessageParts` uses indexed message/order pagination. Global shared attachments/documents/provenance use `threadId:null`; ambiguous thread-scoped queries for those shared collections are explicitly rejected. Search/source relationship views can add dedicated contracts later.

Plan 03 review corrected three earlier plan 02 representation limits:

1. Message holds `partCount`, not a list of every part ID. Parts own `messageId`/`order`. An output can accumulate arbitrarily many bounded parts without growing its Message record or response manifest.
2. Text/Note contains exactly one inline string of at most 16,384 UTF-16 code units or a content-addressed UTF-8 text-blob reference. `inlineTextSegments` yields bounded, ordered segments without splitting a surrogate pair; streaming adapters persist additional parts instead of repeatedly extending an unlimited inline string. Long imported text uses one verified blob reference and streams through the blob interface. The byte layer must verify UTF-8 for `canonical_text`; the injected checker requires that evidence in addition to hash and size. A generic verified blob is insufficient. Oversized structured/tool payloads remain raw source/artifact references with compatibility metadata; importer adaptation is still required.
3. Thread/branch tombstones record a bounded root scope, not every descendant ID. SQL resolves visibility and moves active selection to the closest retained ancestor. Local writes cannot grow a deleted thread/subtree. The root scope continues to hide descendants; multi-device ordering/conflict handling remains plan 25 work.

These corrections remove archive-size-dependent control payloads. The staged publication system below handles complete threads and sealed messages spanning many control requests. Provider parsing and adaptation consume it in plan 04; the presence of normalized fixtures does not claim that a real provider export importer is implemented.

## Hidden normalized import groups

The additive core import controls preserve the existing 24 canonical mutation commands. `beginNormalizedImport` assigns one caller-owned import/group ID and declares a target thread. Create mode requires a new thread and its explicit ThreadState; extend mode requires the existing thread revision and only adds immutable records, preserving user title, active selection, tags and other state. Imports contain sealed messages and terminal attempts; an export cannot manufacture a live generation producer.

`stageImportRecords` accepts at most 128 individually shape-validated records in a 1 MiB envelope. Each record has its own stable operation ID and recorded time. Ordered control sequence, record ordinal and a rolling manifest digest are durable. The records remain in `quixi_import_records`, separate from canonical reads and sync rows. No staged record can satisfy another job's references. Global Quixi identities and scoped provider identities are reserved across active groups and fenced against ordinary canonical inserts. Cancellation releases staged entity/source reservations; record operation identities remain reserved to prevent later reuse with a different meaning. At most eight active groups bound owner bookkeeping, while completed/cancelled metadata remains durable for replay.

The first `validateImportStep` freezes staging. A persisted topological pass visits at most 128 messages per control, decrementing indexed dependency counts for parent and edit predecessors. Missing links and cycles fail before recursive relationship checks. A second pass validates at most 128 bounded records against this group's records plus committed canonical records, building separate staged edges. SQL counts and the unique part-order index verify complete, consecutive message parts; no whole thread or manifest enters JavaScript memory. Parts can only belong to a new staged message, so this route cannot append to sealed existing history. Imported extensions cannot grow a tombstoned subtree.

Validation evidence belongs to the current repository instance and current live sync high-water. A storage-owner restart or intervening canonical commit requires a new incremental validation pass; ThreadState revision is checked again. The worker uses `importValidationRecords` to read exactly the next bounded candidate record set, with no SQL statement held across asynchronous blob verification. Finalization repeats synchronous catalog checks because a corrupt-file read may quarantine a blob without creating a sync operation. Blob files are verified/published before SQL; their durable import-to-transfer mapping remains until later bounded cleanup succeeds, including after cancellation or owner loss.

`finalizeNormalizedImport` requires the frozen expected record count and manifest digest. One synchronous SQL transaction copies records and edges with `INSERT…SELECT`, appends ordered `ImportRecord` sync operations and one `PublishImport` marker, records the publication/control result, and clears staged payloads. No canonical reader or sync page can observe an intermediate graph. A failure, including SQLite allocation denial, rolls back all canonical/sync writes and retains retryable staging. The final SQL transaction is allowed to scale with the group size; JavaScript memory remains bounded. Cancellation is honored before this atomic phase, and cannot promise to interrupt an already executing commit. A lost final reply requires retrying the same IDs or reading status.

Sync receivers must stage every `ImportRecord` by import ID and ordinal until its matching `PublishImport` supplies and verifies the total count and manifest digest. They must not apply individual sync pages as visible partial graphs. The digest starts with 64 zeroes and chains `SHA256(canonicalJson([previousDigest, operationIdentity]))`, where each identity hashes the canonical record operation envelope (version, operationId, kind, recordedAt, payload). The marker has no additional record effects. Import records receive local sequences only at final publication, so concurrent ordinary commits cannot make an inspection cursor skip earlier hidden sequence numbers. This establishes grouped operation semantics, not Cloud transport, encryption or conflict resolution.

Every successful control caches its exact result and argument identity. `committedImportOperation` allows replay checks before external byte work. Cached results are historical snapshots; `normalizedImportStatus` reports current state. In particular, replaying an old ready response after restart does not recreate validation authority. `readStagedImportRecords` provides bounded inspection until publication/cancellation clears those payloads.

## Blob publication and interrupted generations

The repository receives `assertBlobAvailable(sha256, byteLength, stagedBlobIds, requiredEncoding?)`. It performs only synchronous catalog checks. The byte/catalog layer verifies and publishes files before the canonical transaction; successful canonical commit permits staging cleanup afterward. This ordering can leave recoverable orphan files on SQL failure, but cannot claim SQLite atomically committed filesystem writes. Text/Note supplies `requiredEncoding:'utf-8'`; other byte references do not. Raw source/attachment/document references remain canonical; transfer recovery bookkeeping is local infrastructure and does not itself emit history sync operations.

Reopening the database or acquiring the storage-owner lock does not prove a generation producer died: its HTTP stream may still run in a follower tab. `recoverInterrupted` therefore requires an explicit bounded list of **confirmed lost producer generation IDs**, supplied by the coordinator after lease/registration reconciliation. It changes streaming attempts to `partial`, seals retained output and records a visible recovery event with sync operations. It never invents successful completion or discards a received prefix. Repeating recovery for terminal attempts is a no-op. Establishing actual producer-loss evidence remains coordinator integration work.

## Acceptance and limits

The private WASM SQL suite validates all 24 mutation kinds, all three synthetic conversation shapes, close/reopen retention, raw/provenance links, source uniqueness, exact retries/conflicts, optimistic revisions, precommit rollback, migration failure rollback, FK/integrity checks, SQL immutability guards and independent trigger-audited record-to-sync coverage. It also validates monotonic sync paging, confirmed recovery, 1,001-part output metadata staying constant-sized, and deletion of a 50,000-message thread with a command under 2 KiB. The declared 50 MB text-blob test checks metadata and injected verification requirements; it does not allocate or claim to have persisted 50 MB of bytes.

Run:

```sh
npx tsc --noEmit -p packages/storage/tests/canonical/tsconfig.json
node --experimental-transform-types --test packages/storage/tests/canonical/*.test.ts
```

The suite checks the WASM artifact against the pinned manifest before opening SQLite. Browser/OPFS durability, quota and real UTF-8 byte verification require the separate owner-worker/browser tests. The import suite additionally proves all three normalized fixtures (including a captured native stream marked partial), hidden staging across close/reopen, exact control replay, source/global-ID overlap fences, missing/cyclic references, a sealed 2,000-part message carried across more than 2 MiB of bounded controls, revoked UTF-8 blob evidence, durable transfer cleanup links and atomic publication rollback under `SQLITE_FULL` page-allocation denial. This allocation test is not a browser-quota test. A 50,000-message child-before-parent import stages without building a JavaScript graph; a local run took approximately 3.9 seconds staging, 10.1 seconds validation and 1.1 seconds final publication. Timings are evidence for this machine/run, not a performance guarantee.

The production client/worker [browser acceptance](../validation/archive-client.md) separately covers real OPFS, two-tab ownership/failover, a 1,001-part imported message with a verified UTF-8 blob, hidden staging/publication, cancellation cleanup and owner/process restart in Chromium and WebKit. Migration recovery/export UI, provider normalizers and producer lease reconciliation remain separate plan work.
