# 0010 — Portable archives and independently readable exports

Status: accepted format and snapshot mechanism; implementation in progress. Activation UI, supported-host release qualification and large-archive stress gates remain open.

## Product requirements

[Archive export](../product.md#98-archive-export) requires portable SQLite, blobs and a manifest. [Open export](../product.md#99-open-export) requires JSONL and Markdown that ordinary tools can read. [Raw preservation](../product.md#21-raw-provider-preservation), [import transactions](../product.md#27-import-transactions) and [sync history](../product.md#96-synchronization-operations) require exact source bytes, identities, branches, provenance, tombstones and operation receipts. Restore creates another archive; it does not import/merge records into the active history.

## Version 1 container

The portable output is an uncompressed standard TAR/PAX file. Entries are ordered `format.json`, `quixi.sqlite`, sorted `blobs/<sha256>`, `checksums.jsonl`, then `manifest.json`. Only regular files and size-only PAX headers are accepted. The parser rejects duplicate or unexpected paths, links, traversal, unsupported extensions, malformed headers/checksums, missing end markers and non-padding trailing data. TAR remains readable with ordinary tools; see the [GNU TAR format reference](https://www.gnu.org/s/tar/manual/html_node/Standard.html) and [portability guidance](https://www.gnu.org/s/tar/manual/html_section/Portability.html).

`format.json` declares `format: "quixi-archive"`, `version: 1` and `kind: "portable" | "open"`. A third kind, `"rescue"`, uses the same container and entry order for the byte-level recovery export defined in [ADR 0016](./0016-startup-failure-and-schema-recovery.md); its manifest carries a `recovery` block instead of canonical counts. Restore accepts a rescue archive only at exactly this build's schema, cleans its raw database into a fresh candidate with the same step exports use, derives the canonical summary from that candidate, and drops unreferenced blob files; other schema versions are refused by name. Each inventory JSONL line has `path`, `byteLength`, and `sha256`; the inventory excludes itself and the final manifest. The manifest binds inventory digest/length/count, ordered migration ledger, canonical and sync counts/high-water, streaming-generation count, the default workspace ID and the exclusion policy. Metadata is at most 64 KiB; inventory lines are at most 1 KiB. Hashes detect corruption, not author identity or authenticity.

Open output substitutes `records.jsonl` and `history.md` for SQLite. JSONL includes complete canonical records and sync envelopes. Markdown identifies every record and includes full inline/blob-backed textual parts; IDs, parent links, roles, filenames, generation metadata, tombstones and provenance remain available as plain metadata. Binary/raw bytes use the same digest filenames. There is one shared canonical representation and no embedding dependency.

## Consistent, clean SQLite snapshot

The actual pinned WASM and SAH-pool combination supports `sqlite3_file_control(SQLITE_FCNTL_FILE_POINTER)` and VFS `xRead`. A read transaction freezes the source while its owner serializes foreground writes. A 64 KiB WASM scratch buffer streams pages through `SAHPool.importDb(name, callback)` into a private snapshot. This avoids the whole-database allocation of `exportFile()`; `sqlite3_backup_*` is not exported by this build. See SQLite's [file-control API](https://sqlite.org/c3ref/file_control.html), [VFS methods](https://sqlite.org/c3ref/io_methods.html) and [SAH-pool persistence API](https://www.sqlite.org/wasm/doc/trunk/persistence.md).

The raw snapshot is never exported. A fresh database is initialized from trusted migrations and populated using bounded row copies. Deleting private tables from a copied database would leave excluded bytes in unused pages. The clean copy preserves canonical records/edges, sync operations and sequence state, transaction receipts, published import jobs/identity/control receipts, referenced blob catalog entries and only `quixi_local_state.defaultWorkspaceId`. All workspace IDs on canonical records remain intact. Provider credentials, keychain associations, producer leases, unfinished imports, host staging, derived search data and model assets are excluded. Exported catalog entries require byte verification again after restore.

Each blob is verified through the canonical byte catalog and copied in 64 KiB ranges to one reusable private disk file. The catalog parent/range leases close before an export step returns; eight foreground byte leases pause export until resources are released. The temporary copy is streamed into TAR or Markdown. Output and checksum inventory are disk-backed; there is no whole-archive JavaScript array or ZIP object.

The initial source snapshot, candidate SQLite import and individual blob verification/copy can exceed one step's wall time. They yield/check cancellation between 64 KiB blocks, but `maxBytes` is not a time limit for those phases. Amendment (2026-09-13): the source snapshot is now copied in steps. `SnapshotCopier` opens the target as a pool database first (so its handle is associated with its name: the pool's chunked import keeps an unassociated handle until it finishes, which any other file open between steps could take and corrupt the copy), holds the source read transaction across `advanceArchiveJob` calls, and copies at most `maxBytes` per step in 64 KiB blocks through the VFS (`openSqliteFileWriter`, the write-side twin of the bounded reader), reporting `completedBytes`/`totalBytes` for the `snapshot` phase; the finished file is closed and reopened before it is read. Releasing or failing the job closes the copier, which releases the read transaction and unlinks the incomplete private output. The 1M-message stress run forced this: a 4.7 GB snapshot in one step outlived the client's 60 s reply deadline. The restore's candidate import takes the same path (`BoundedFileCopier` over the received `incoming.sqlite3`, at most `maxBytes` per step into the candidate pool), and the candidate's whole-file `integrity_check` before record validation is now one table (with its indexes) per step, so a step's cost is bounded by the largest table rather than the file; callers request `advanceArchiveJob` with `INTEGRITY_CHECK_DEADLINE_MS` for that reason. Individual blob verification/copy remains as stated. The record validator's graph phases are set-based since 2026-09-13: the message/edit topology check runs Kahn's algorithm in batches of up to 32 nodes per budget unit (three statements per batch through the parent and edit indexes) instead of one node per statement, the DFS interval labelling is gone, and ancestry and tombstone visibility are recursive up-walks over parent links (bounded by the acyclicity the topology phase has just proven and a depth cap); the restore of a 1,000,000-message archive validates in 89 minutes where the per-node walk ran for hours. The clean copy now fetches a step's remaining row budget in one ordered statement instead of one `LIMIT 1` statement per row, and each step's inserts commit in one transaction instead of one autocommit (journal write and sync) per row; on the 30,000-message archive-scale proof in Chromium the portable export fell from 430 s to 58 s, the restore validation from 178 s to 86 s and the open export from 399 s to 68 s (the eighth 1M run still exports with the earlier bundle); each restore validation step likewise commits its scratch writes once (restore 86 s to 78 s on the same proof); the open format's encoding phase reads records and operations in blocks of 64 per statement while still yielding one record per step unit; the portable format streams the clean database file and has no per-record statements. SQLite `integrity_check` is still a synchronous scan. SQL row work is bounded by record count and existing record/control sizes; large-archive latency needs separate qualification. The active SAH pool reserves ten files and failed pool allocation/copy unlinks only private names.

## Isolated restore and activation barrier

The receiver writes fixed paths into a fresh candidate UUID namespace. It verifies TAR structure, input length/hash and the checksum inventory before treating SQLite as a candidate. Candidate connections use read-only/query-only mode, defensive settings, disabled triggers and untrusted schema settings. Exact approved table/index/trigger SQL definitions and migration ledger must match this build before canonical data validation. Arbitrary supplied SQL is never run as a migration.

Validation uses SQL-backed graph queues, ancestor intervals, part counts, blob references and journal coverage. It checks canonical shapes and edges, message/edit cycles, context predecessors, generation backlinks/lifecycle, tombstoned active branches, tool-result ancestry, operation digests/effects, transaction receipts and published import groups/identity receipts. All referenced blobs are hashed again; text blobs undergo fatal UTF-8 decoding. Missing and unreferenced blob entries fail validation. The prior active canonical state is untouched.

Jobs and their operation receipts are durable, transfers are owner-local, and byte windows are 64 KiB/four credits. Interrupted working jobs become failed on owner reopen. Bounded job listing exposes outstanding ready exports; a later begin cleans at most one failed/cancelled job. Explicit release removes private staging while retaining a validated candidate namespace. A ready candidate must be revalidated under a new owner before review; the readonly VFS bytes must still match the received database checksum.

`prepareArchiveActivation` records a review token bound to exact candidate summary and current source archive/sync revision. This token is not user consent. `withActivationReview` checks the durable token, acquires the candidate's archive-owner Web Lock, reruns complete candidate validation, checks the summary and source revision again, and invokes the selection-pointer callback while holding the lock. Busy or corrupted candidates cannot reach that callback. Profile selection, durable activation receipts and explicit replacement UI belong to [ADR 0012](./0012-archive-selection.md) and root integration; this decision does not claim their acceptance. Restored streaming prefixes are preserved exactly; producer-loss recovery must be explicit canonical operations during activation/startup.

## Browser file boundary

The shared workflow prepares disk-backed host staging before a separate Save user gesture. Existing ready export jobs can be staged again without creating another snapshot. Lost successful begin replies are recoverable because the workflow allocates the stable job/operation identity before dispatch. Release retries preserve their operation identity.

Browser file-save staging uses OPFS writable streams, 64 KiB chunks, incremental hashing and disk readback verification. Provider request staging retains its separate explicit 8 MiB limit. Safari 26 added writable streams; runtime capability checks remain authoritative ([WebKit implementation discussion](https://bugs.webkit.org/show_bug.cgi?id=231706), [Safari 26 release notes](https://developer.apple.com/documentation/safari-release-notes/safari-26-release-notes)). There is no large in-memory fallback when private writable storage is unavailable.

A native browser save picker receives bounded writes and commits only by closing its destination stream. The download fallback uses an OPFS-backed `File`. Removing the underlying entry can invalidate that file ([File System API](https://fs.spec.whatwg.org/#api-filesystemfilehandle-getfile)), so transfer release never deletes handed-off download files. Up to four download files are retained per composition-owned profile namespace, including across reload. `fileSaveCapability`, `listTemporaryDownloads` and `clearTemporaryDownload` support an explicit “download completed / clear temporary file” action. Browsers provide no completion callback; neither a timer nor a returned save promise proves download completion. Temporary metadata contains only opaque ID, filename, byte length and creation time. Web Locks protect live stages; bounded cleanup removes abandoned non-download staging. Retained files require explicit cleanup.

## Evidence and remaining gates

- Thirteen pinned-WASM/codec tests cover independent system-TAR extraction, fragmented input, PAX headers, corruption/truncation/path/link rejection, bounded VFS copy, cancellation, private-page exclusion, allocation/copy failure, unexpected executable schema, cycles, edge/journal damage and orphan published imports.
- The [browser report](../../packages/storage/tests/archives/results/snapshot-browser.json) includes actual Chromium/WebKit OPFS snapshots, canonical branch/provenance/tombstone/generation/published-import round trips, exact journals/raw bytes, full blob-backed Markdown, production-client 9 MiB transfers, foreground lease pressure and owner-restart revalidation. Activation callback tests hold the real candidate lock and corrupt actual candidate bytes.
- The schema-8 refresh passes in both engines and records all eight migration names/checksums. It round-trips text appended across the two reserved transport-provenance kinds, including embedded NUL/Unicode, and verifies complete Markdown text. A genuine schema-7 portable built from immutable migrations 1–7 is refused at `schema_validation` by name at the schema-8 upgrade floor before any candidate is cleaned; no ready candidate is produced and active canonical records/sync operations remain unchanged. Since 2026-09-09 a genuine schema-8 portable holding the source's rows restores through the candidate upgrade of [ADR 0016 §3](./0016-startup-failure-and-schema-recovery.md) with identical records and journal, and stays ready across owner restart. TAR format version 1 is unchanged: its manifest already declares the exact SQLite schema/ledger.
- Browser host acceptance includes an actual 32 MiB download in both engines, immediate transfer release, reload, digest verification by an independent Node stream, and explicit retained-file cleanup. Injected picker mechanics use real OPFS destination streams and prove 64 KiB writes plus cancellation preserving an existing file; this is not automated OS save-dialog acceptance.

Cross-host portable file exchange, actual Tauri archive workflow/UI, very large archives, measured peak memory/disk amplification, capacity preflight, abrupt process/quota faults in every restore phase, pre-schema-8 compatibility and complete replacement UX remain release gates. Browser WebKit evidence is not installed Safari or Tauri evidence. Playwright WebKit required a regular persistent context for OPFS; test namespaces remain independently random because this runtime can share origin storage across profile paths.

## Amendment (2026-09-12): capacity check before a job begins

`beginArchiveExport` and `beginArchiveRestore` now compute what the job will
write on OPFS — an export: the database file (`page_count × page_size`) plus
every catalogued blob's bytes; a restore: twice the announced container size
(the received bytes and their validated candidate copy) — add 8 MiB of slack
and compare it with `navigator.storage.estimate()`. When the browser reports
less free space, the job is refused before any output exists, as
`QUOTA_EXCEEDED` with both numbers in the message; when the estimate is
unavailable or malformed the job proceeds and the browser's own quota error
still stops it safely, as before. The decision is a pure function
(`packages/storage/src/worker/archives/capacity.ts`) with unit tests; the
repository option `estimateStorage` lets tests inject an estimate.
