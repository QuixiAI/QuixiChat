# 10 — Add routing and cross-provider continuation

**Status:** In progress (compatibility reports, switch review, recorded events, per-conversation routing and reusable aliases; [ADR 0017](../decisions/0017-provider-switch-inspection.md))

**Workstream:** A6 — portability and switching

**Depends on:** [06](./06_integrate_live_providers.md), [08](./08_build_chat_and_library_ui.md)

## Outcome

Allow a user to continue an existing conversation with another provider while inspecting transformations, account selection, privacy changes, and context constraints.

## Tasks

- [x] Implement model aliases and routing profiles with ordered candidates, capability requirements, account health, privacy class, context, region, and cost constraints. Implemented and qualified (2026-09-10): a per-conversation routing profile holds a name, ordered fallback candidates, tool/image/context/cost requirements and the privacy allowance; the route is chosen before the first attempt from the candidates' account health, privacy class, catalog capabilities and context window, the counted prompt's estimated cost and the compatibility report, with every examined candidate's outcome shown and a routed attempt recorded as an `AutomaticFallback` event ([ADR 0017](../decisions/0017-provider-switch-inspection.md), [routing tests](../../packages/app/tests/switching/routing.test.ts), [shared-app check thirty](../validation/shared-app.md)). Reusable aliases are now implemented: Preferences creates/edits/reorders/deletes a bounded registry, and explicit composer review applies a complete primary/fallback/constraint snapshot to canonical ThreadState; later edits/deletion cannot reroute it ([alias acceptance](../validation/routing-aliases.md), [ADR 0018](../decisions/0018-local-preferences-and-routing-presets.md)). Cost enforcement is now implemented before every attempt ([cost acceptance](../validation/request-cost-limits.md), [ADR 0022](../decisions/0022-per-attempt-request-cost.md)): a separate total cap includes input plus selected maximum output, legacy input caps remain independent, missing counts use a conservative context budget, exact-request counts require explicit action, and send/regeneration/fallback/summary guards refuse before writes or generation HTTP. Version-4 alias/profile snapshots, malformed-limit refusal, exact decimals, both-engine wire/restart checks and portable restore are verified. The region design prerequisite is reviewed in [ADR 0023](../decisions/0023-regional-processing-evidence.md): the current OpenAI snapshot supports a positive US/EU path, while Haiku 4.5 rejects `inference_geo`; account and relay evidence, counting guards, configuration-bound reviews and the required host/persistence matrix are specified. Native US/EU connection setup is now implemented and verified ([native regional connections](../validation/native-regional-connections.md)): exact native registry evidence, separate credential bindings, explicit session eligibility, separate image approval, stale-adapter/last-dispatch refusal, 29 native checks and 11 settings groups per browser engine. Conversation constraints are now integrated through version-5 profiles/aliases, initial selection, count/send/regenerate/fallback and summaries, with stale-policy/evidence guards and canonical attempt/routing explanations; 268 affected Node tests, 42 browser groups per engine and exact portable restore pass ([policy validation](../validation/processing-region-policies.md)). Regional web configuration and authenticated identity verification are now implemented: real app → relay → hostname-verified regional TLS fixtures pass 9 groups per engine; unknown/changed declarations and policy changes during the handshake transmit no additional content ([web relay validation](../validation/regional-web-relays.md)). The integrated native gate is now closed: the actual Tauri shared app uses unchanged US/EU HTTPS registrations with a hostname-verified synthetic TLS fixture, real scoped Keychain credentials and canonical worker storage. Sixty-three checks in five native processes cover certificate refusals, constrained send/regeneration/summary, initial wrong/unknown region, fallback refusal, late policy change, eligibility revocation and exact restart provenance; eight expected HTTP requests reach the fixture. The combined ADR 0023 matrix is assessed in [native attempt validation](../validation/native-regional-attempts.md). This qualifies controlled host behavior, not physical geography or real account eligibility.
- [x] Build a compatibility-analysis step that compares the canonical active path with the target model and produces preserved/transformed/omitted/blocked items. `analyzeCompatibility` runs the same mapping as `prepare` and reports preserved parts by kind, blocked parts with the mapper's codes, request-level constraints and the encoded request size; the chat workflow adds what it omits (internal provenance records, empty assistant turns) and transforms (text inlined from stored bytes). The shared workflow also reports reviewed attachment markers and reviewed-summary prefix replacement as transformations. Evidence: [compatibility tests](../../packages/providers/tests/compatibility.test.ts) and [shared-app check twenty-six](../validation/shared-app.md).
- [x] Implement the Compatibility Inspector with inspectable source-to-request transformations, context estimates, and available cost metadata. Require a deliberate user choice for consequential lossy or privacy-changing transitions. The composer shows the report (counts by kind, blocked reasons, constraints, request size, privacy-class change, different-provider notice), the target's context window, requested output and input room, the on-request token count's fit or excess against that room, and the reviewed rates with an input estimate plus a bounded output estimate once a count exists; it refuses to send a consequential switch (connection change, privacy-class change, anything transformed, omitted or blocked) until a review scoped to that exact report is ticked, and refuses a report that is not sendable or a count over the room. Counting stays an explicit action because it sends the branch to the target ([ADR 0017](../decisions/0017-provider-switch-inspection.md)). Evidence: [switch context tests](../../packages/app/tests/switching/context.test.ts) and [shared-app check twenty-six](../validation/shared-app.md). Limits: transformations are shown as counts by kind rather than per part, a connection without a count endpoint gets the encoded request size instead of a token estimate, and regenerating an earlier turn is gated by the active branch's report.
- [x] Implement portability statuses with explicit reasons and keep them current when content, target capabilities, or routing profiles change. The open conversation shows Fully portable, Portable with transformations, Provider-dependent, Blocked or Unknown for its active path across every configured connection's reviewed models, with one reason per target in the adapter's own terms and what is never sent; it is recomputed live whenever the path, the configured targets or the output setting change, so it cannot go stale ([ADR 0017](../decisions/0017-provider-switch-inspection.md)). Evidence: [portability tests](../../packages/app/tests/switching/portability.test.ts) and [shared-app check twenty-seven](../validation/shared-app.md). Limits: this assessment covers every configured target independently of which candidate the conversation profile selects; library-wide status counts and filtering wait on plan 12's stored assessment.

Attachment exclusions are implemented and verified: bounded metadata review/cancel, immutable context plus event, exact occurrence markers in counting/send/regenerate, unchanged originals, restart and portable restore ([acceptance](../validation/context-compaction.md), [ADR 0019](../decisions/0019-reviewed-context-compaction.md)). The summary design prerequisite is complete in [ADR 0020](../decisions/0020-reviewed-summary-proposals.md): typed proposal/input provenance, an unselected generation context, review/apply lifecycle and prefix/tool/branch bounds have [24 design checks per runtime](../validation/context-summary-design.md). The full production proposal → review → apply/clear path is now implemented and verified ([summary acceptance](../validation/context-summaries.md)): frozen verified input, isolated purpose-labeled attempts, separate usage, edited text, stale-source/output/digest refusal, required atomic audit events, bounded prefix-aware requests, cancellation/reconciliation, restart and schema-12/protocol-4 archive/client proofs. Ten authored quality fixtures are prepared; zero actual model runs have been scored. Explicit fresh branching is now implemented under [ADR 0021](../decisions/0021-fresh-context-branches.md): scope-bound review, retained system prompt/routing/draft, empty active selection, atomic context/branch/summary-clear events, exact pending replay and original-history navigation ([branch acceptance](../validation/context-branches.md), 37 browser groups per engine and both portable proofs). All three choices are implemented; this task remains open for actual summary fidelity qualification.
- [x] Implement fallback policy using account health and capability constraints. Make partial attempts and automatic fallback separate Generation records and record a fallback event. A conversation stores one fallback target and whether it may change the privacy class; after a primary attempt fails or ends partial, the candidate's account health, privacy class and compatibility report decide in the open, a user stop never falls back, the fallback is a separate attempt under the same turn, and its `AutomaticFallback` event is committed with that attempt ([ADR 0017](../decisions/0017-provider-switch-inspection.md)). Evidence: [fallback tests](../../packages/app/tests/switching/fallback.test.ts) and [shared-app check twenty-eight](../validation/shared-app.md). Since 2026-09-10 the candidates are an ordered list tried in turn, and a primary whose health blocks sending is routed around before the first attempt (task 1).
- [x] Persist routing state and switching events atomically with their canonical effects. Define confirmation reuse only for the specific approved transformation/privacy scope. Partial: a reviewed switch is committed as a `ProviderSwitch` thread event in the same transaction as the user message it applies to, and the review key (thread, leaf, target, counts, privacy classes, blocked codes) is the confirmation scope. The per-conversation profile is stored by the canonical `SetRoutingProfile` mutation, and routed/fallback attempts commit their events with their generation. Reusable aliases are separate conditional local metadata; applying the exact reviewed snapshot saves the complete canonical routing profile with one sync operation, clears previous switch review/counts and never rereads a newer alias. The forced SQL pre-commit failure leaves neither profile nor operation, and successful application, immutable copies after alias edits/deletion, a fresh provider review and restart all pass ([alias acceptance](../validation/routing-aliases.md), [ADR 0018](../decisions/0018-local-preferences-and-routing-presets.md)). Summary apply/clear likewise require the selected predecessor, expected revision and matching audit event in one batch; unknown outcomes reuse the exact original transaction ([summary acceptance](../validation/context-summaries.md)). Fresh branching now likewise commits its exact context clone, null selection and required branch/summary-clear events atomically; replay restores the recorded selection including null ([branch acceptance](../validation/context-branches.md)). Version-4 cost profiles likewise retain the exact reviewed alias snapshot, and fallback events record their per-attempt cost basis ([cost acceptance](../validation/request-cost-limits.md)). Version-5 regional policies also preserve exact aliases, fresh branches and portable snapshots; routing/attempt history records the region review basis ([policy validation](../validation/processing-region-policies.md)). ## Acceptance criteria

- [x] An imported or native conversation can continue with a different supported provider without rewriting its original history. Native: an Anthropic conversation continues with the OpenAI connection, existing records are unchanged and the switch is a new event (shared-app check twenty-six). Imported: the synthetic ChatGPT export, imported through the production import panel, continues with the Anthropic connection from a text branch after the artifact-bearing branch is shown blocked, with its sketch without exported bytes shown as a transformation and sent as a note naming the file, the switch reviewed from the import origin and every imported message and part unchanged afterwards ([shared-app check twenty-nine](../validation/shared-app.md), [ADR 0017](../decisions/0017-provider-switch-inspection.md)).
- [x] Lossy transformations and compaction are visible before use; the actual transmitted request agrees with the reviewed report. Transformations, omissions, the context room and the counted prompt's fit are visible before use, and the report is produced by the same mapping that builds the request ([ADR 0017](../decisions/0017-provider-switch-inspection.md)); reviewed attachment exclusions now use the same effective-context builder for inspection/count/send/regenerate and preserve source history ([acceptance](../validation/context-compaction.md)). The summary path now freezes the exact transmitted proposal input and carries the reviewed summary through count/send/regenerate/fallback; an additional failed-primary/fallback pair carries the same attachment exclusion marker ([summary acceptance](../validation/context-summaries.md), 35 browser groups per engine). Fresh branching explicitly reviews the retained system prompt and omitted earlier messages/summary; count, primary and fallback bodies contain only that prompt and the new draft, with original records unchanged ([branch acceptance](../validation/context-branches.md)). This closes visibility/request agreement for all three choices; actual summary fidelity remains an independent requirement in task 5. Over-room prompts still require explicit user action.
- [x] Fallback does not silently cross a disallowed privacy class, violate capability requirements, or present partial output as a completed answer. A privacy-class change is refused unless the conversation's policy allows it and the allowance is recorded in the event's reason; a candidate whose report refuses the path or whose health blocks sending is refused with that reason; a partial primary attempt keeps its status and committed text on a sibling branch while the fallback's complete answer is the active path (unit tests for every refusal, shared-app check twenty-eight for the applied, partial and stopped cases). A manual switch likewise cannot cross a privacy class without a review.
- [x] Switches, compactions, and fallbacks remain inspectable after reload. Switches: proven (the recorded event is listed after a browser restart with no connection configured). Fallbacks: the event and stored policy are canonical records; the policy and the fallback event listing are now asserted after restart in the summary browser proof. Attachment exclusion snapshots/events survive canonical close/reopen and portable restore; the browser restarts with the selected policy and a checked review choice. Summary proposals, frozen inputs, edited applied text and summary/fallback event listings survive restart; clear works without a configured provider and preserves exclusions ([summary acceptance](../validation/context-summaries.md)). Fresh-branch and matching summary-clear events are displayed after a full process restart without configured credentials, alongside the restored empty selection and navigable original root. Exact events, context and selection also survive portable restore ([branch acceptance](../validation/context-branches.md)).
