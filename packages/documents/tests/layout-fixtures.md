# Authored PDF layout oracle

These fixtures describe intended reading structure before the normalizer is
implemented. Expectations come from authored text, coordinates and visual page
review, not from running Quixi normalization. `fixtures/layout-manifest.json`
contains the exact lines, cell matrices, page numbers, sizes and SHA-256 values.
Its `kind` fields label the author's intent; they do not prescribe a new public
block-type API. The ordinary fixture generator/manifest are unchanged.

Regenerate only these three PDFs and their separate manifest:

```sh
uv run --with reportlab==5.0.1 --with pypdf==6.18.0 --with pillow==12.3.0 --with charset-normalizer==3.4.7 python packages/documents/tests/generate_layout_fixtures.py
```

ReportLab `invariant=1` fixes document metadata/IDs. All pages are 612 by 792 PDF
points, with a bottom-left origin. Fonts are the built-in Helvetica and Courier
families; no system font, downloaded font, current time or random data enters
generation. No existing fixture is regenerated by this command.

## Two columns: `layout-columns.pdf`

Both pages have a heading and footer spanning the column region. Body columns
start at x=48 and x=336. Within each column, a 42-point baseline gap separates
paragraphs, while wrapped lines use 15-point leading. On each page the required
block order is:

1. `P{page}-TITLE` heading.
2. The complete `P{page}-L1` paragraph, including its two continuation lines.
3. The complete `P{page}-L2` paragraph, including its continuation line.
4. The complete `P{page}-R1` paragraph, including its two continuation lines.
5. The complete `P{page}-R2` paragraph, including its continuation line.
6. `P{page}-FOOTER`, after both columns.

The generator deliberately draws the right line before the left line at every
baseline. A content-stream concatenation therefore alternates columns. A simple
row-major geometric sort also alternates columns. Neither matches this oracle.
Lines within each prose paragraph may join with a single space; paragraph,
heading and footer boundaries must remain distinguishable. Page two is a new
page, never continuation text attached to page one's footer. The exact block
text is in `expectedBlocks`, not inferred from anchor names alone.

## Table and indented text: `layout-table-code.pdf`

Page one contains four ruled rows and three separately drawn cells per row.
The reading order is the heading, then this row-major cell matrix, then the
`TABLE-AFTER` paragraph, then the footer:

| Item | Quantity | Note |
| --- | --- | --- |
| amber | 7 | warm sample |
| cobalt | 12 | cool sample |
| jade | 4 | green sample |

Cells start at x=60, 224 and 390; their baselines are y=688, 649, 610 and 571.
The content stream draws the entire Note column first, then Item, then Quantity.
Output must retain cell boundaries and each quantity's row association. Tabs,
spaces or another explicit structural representation may separate cells; there
are no literal pipe characters in the PDF text to copy or claim as original.

Page two reads heading, two-line introduction, one eight-line code block, the
list, the two-line `CODE-AFTER` paragraph, then footer. The exact code is:

```js
// CODE-START: nested accumulation
function total(values) {
  let sum = 0;
  for (const value of values) {
    sum += value;
  }
  return sum; // CODE-END
}
```

These lines use Courier at x=64 and 15-point leading. Two-space and four-space
indentation are literal characters in their PDF string operands. Preserve the
code's line boundaries and indentation rather than flattening it into prose.
The list below it is a separate block with these exact authored lines:

```text
1. LIST-ONE: Pack the amber map.
   Keep the folded copy with the original item.
2. LIST-TWO: Check the violet compass.
   a. LIST-NESTED: Record the northern bearing.
3. LIST-THREE: Close the copper case.
```

The second line continues the first item. The nested `a.` line belongs under
item two. `CODE-AFTER` must not be absorbed into the final list item. A parser
may encode leading spaces as positioning instead of text; any reconstructed
indentation must be represented honestly in source mapping.

## Unsupported geometry: `layout-unsupported.pdf`

The page has ordinary horizontal text and two distinct text objects rotated
90 and 45 degrees. All seven exact source anchors are listed in the manifest.
The raw extraction must retain those anchors and the transforms that identify
the rotations. A normalizer without mixed-orientation support must expose an
explicit unsupported-layout outcome rather than silently dropping, sorting as
horizontal prose, or stitching the rotated strings into surrounding sentences.
This fixture intentionally does not prescribe a supported reading order for the
mixed orientations.

RTL is **not covered**: the pinned ReportLab font bundle has no verified
RTL-capable face for this test. Missing-glyph substitutions would not constitute
an RTL fixture. A separately pinned, licensed font and language-specific oracle
are prerequisites for adding that gate.

## Original-source anchoring requirements

- Every emitted non-whitespace source span must identify its original page and
  actual source text item/range. Slicing those original inputs must reproduce
  the source characters, including punctuation and case.
- Reordering columns/table cells may make source item indices non-monotonic.
  Do not invent a contiguous raw source range for a paragraph assembled from
  interleaved items. Each contributing range remains traceable.
- Column anchor strings must stay attached to their own continuation lines.
  The table's quantities must map to their correct cell and row. Identical words
  on different pages must keep distinct page identities.
- Joining prose line wraps or creating block/cell separators can introduce
  whitespace absent from the raw input. Mark it as reconstructed structure;
  do not attribute it to unrelated PDF text or expose invented pipe characters
  as original content.
- For code/list text, preserved characters and inferred indentation must remain
  distinguishable in the source mapping. A normalized offset is never a byte
  offset into the original binary PDF.

## Fixture validation

On 2026-09-09, two successive pinned generations produced identical bytes for
all three PDFs and the manifest. Independent pypdf 6.18.0 inspection verified
all authored text anchors, five page counts, right-before-left interleaving and
Note-before-Item-before-Quantity drawing order. Poppler rendered all five pages
at 85 DPI; every rendered page was visually inspected with no clipping,
overlapping text or missing glyphs. This validates the fixtures, not the future
normalizer or production PDF worker integration.
