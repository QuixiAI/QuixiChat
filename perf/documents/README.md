# Production PDF persistence performance

This diagnostic exercises the actual `persistPdfDocument` → managed `ArchiveStorageClient` → owner worker → SQLite WASM/OPFS → shared lexical FTS pipeline with PDF.js 6.3.289. It does not replace the parser, persistence calls, blob storage, or search indexing. The current runner starts each case with a fresh browser process/profile and fresh loopback origin, and asserts empty OPFS before source setup. The retained split baseline's earlier launch variants are described below. No provider calls, OCR, inference, user documents, or external browser requests are involved.

Run from the repository root:

```sh
npm ci
npx playwright install chromium webkit
npx tsc --noEmit -p perf/documents/tsconfig.json
node perf/documents/run.mjs
```

The runner also requires `uv` and `ps`. It invokes the same exact fixture-tool pins used by the extraction proof: ReportLab 5.0.1, pypdf 6.18.0, Pillow 12.3.0, and charset-normalizer 3.4.7. An unavailable RSS measurement is recorded as `null` with a reason; functional extraction may still be measured. Select an installed engine with `QUIXI_TEST_BROWSERS=chromium` or `QUIXI_TEST_BROWSERS=webkit`; the shared selector rejects unsupported/duplicate/empty selections. CI should be manual performance qualification, with browser OS dependencies and `uv` installed, and upload `perf/documents/results/production-browser.json` even on failure. No numeric release thresholds are asserted.

The five cases per engine are one, 100, and 1,000 pages of the existing synthetic text PDF; a 31,115,264-byte image-heavy PDF with native text; and cancellation immediately after the first indexed page of a fresh 1,000-page PDF. The 1,000-page document reaches the current page-count admission limit. The image fixture is approximately 29.7 MiB, below the 32 MiB source cap. It is regenerated by `generate_image_fixture.py`, verified using pypdf's actual page/image/text APIs, and hash-described in `fixtures/manifest.json`. The generated PDF is ignored by Git. Reproduce it independently with:

```sh
uv run --with reportlab==5.0.1 --with pypdf==6.18.0 --with pillow==12.3.0 --with charset-normalizer==3.4.7 python perf/documents/generate_image_fixture.py
```

Synthetic fixture content is dedicated under CC0-1.0. Generator/parser/font/CMap dependency licenses and pinned artifact provenance are retained in [the documents third-party manifest](../../packages/documents/third-party/manifest.json) and its accompanying license files. The build emits those license files. This generator uses standard Helvetica PDF references, not an embedded custom font.

## What is measured

- Original bytes and SHA-256, bounded upload chunks, extraction source-read bytes/chunks, largest source-read chunk, total output UTF-16, largest current-page output, and largest staged text/map batch. Source setup streams network chunks into 64 KiB OPFS uploads; setup time is reported separately and excluded from extraction timing. A transport may supply a larger temporary incoming network chunk during setup, so this is not a 64 KiB bound on browser networking internals.
- Time to first publication and first actual page-index credit, total workflow time including cleanup, selected page milestones, and request counts/total/p50/p95/max timings by real public operation. These timings include transport/queue/SQL and observer overhead, not isolated SQL CPU. Percentiles summarize requests within one run, not repeated benchmark runs.
- A real foreground `readEntities` request, bounded to one document and 8 KiB, dispatched immediately after publication without waiting for the publication reply. Page one and every tenth page are sampled, at most 101 probes. The report retains each probe and whether publication had settled first, plus ten pre-extraction baseline reads. This measures a read queued around publication; it is not a claim about all UI interactions, writes, or arbitrary foreground workloads. It adds real contention to the pipeline.
- Cancellation request-to-workflow-drain time, durable interrupted state, first page retained/indexed, zero tracked PDF workers after cleanup, and unchanged canonical/sync record counts. The actual public FTS query must find the first page for each case that received index credit; rejected sources with no published page have no such claim. This is a page-credit cancellation point, not an arbitrary parser-internal cancellation sample.
- Browser-server process-tree RSS sampled using `ps` every 500 ms (plus start/end). Each case retains at most 2,400 raw samples and still tracks peaks/counts beyond that; every case has a 20-minute deadline. Baseline follows original-source setup, immediately before extraction; setup allocation/garbage collection can affect the baseline. The tree includes the browser, storage worker, PDF workers, and shared pages; shared mappings may be counted repeatedly. OS-managed/reparented browser processes may be excluded. Node, OS caches, and other processes are outside the tree. Sampling misses short peaks. Missing readings remain unavailable rather than zero.

A request-observing bound facade delegates to the real client and never changes args or results. It retains bounded numeric samples, not page text/maps or an entire document collection. Request timing arrays have a 10,000-entry per-operation guard. Small output counters are updated before transferring staged requests; original upload lengths are captured before `sendChunk` transfers/detaches their buffers. All admitted foreground probes are awaited before closing the case.

## Interpretation limits

These are single-run, fixed-order synthetic diagnostics on the reported hardware/browser versions, with OS load averages retained. They are not a statistically controlled throughput comparison. Storage caches, JIT, browser subprocess lifecycle, and other development activity can affect results. Source and built-asset SHA-256 fingerprints tie the report to the measured build; the runner checks source stability at completion. The report does not use later source changes as evidence for the captured build.

PDF.js can hold the whole source and allocate decompressed intermediate structures/page item arrays. The 32 MiB source, page/output limits and observed RSS do **not** establish an archive-size-independent or hard parser-memory bound. The image-heavy case stresses source transfer, hashing and parsing; extraction-only PDF.js need not decode that image. It does not establish raster-rendering/decompression memory acceptance. The existing text-page fixture contains short pages, so 1,000 pages do not prove worst-case dense-page/map publication performance. Cancellation after indexed page one does not prove deadline responsiveness inside every expensive parser operation.

No complete-plan or production-scale acceptance follows from these measurements. The retained report is evidence for choosing the next bounded optimization and for comparison with future captures on the same methodology.

It contains no PDF performance result. The associated `nonpersistent-run.mjs.txt` preserves that launch version.

The reusable runner now launches a fresh **persistent** profile for each case, as the existing production persistence acceptance runner does. A fresh profile alone still exposed prior OPFS data on the same origin in this WebKit build; `webkit-shared-origin-isolation-rejection.json` and `shared-origin-run.mjs.txt` retain that failed isolation check. The current runner therefore also gives every case a fresh port0 origin and records it on the case. `continuation-webkit.json` uses that path. The initial Chromium results used `launchServer` plus a nonpersistent context; the report methods/source snapshots preserve this difference, so these split captures must not be presented as a controlled cross-engine comparison. The current runner identifies the browser's unique new live child PID after launch; ambiguous/missing process attribution produces unavailable RSS, not a guessed process tree. Continue selected cases without repeating completed measurements:

```sh

QUIXI_TEST_BROWSERS=webkit QUIXI_PERF_REPORT=continuation-webkit node perf/documents/run.mjs

A successfully captured suite containing those outcomes has status `measured_with_rejections` and exit zero because measurement completed; it is **not compatibility qualification**. Harness failures, inconsistent state, leaked PDF workers, unexpected external traffic, changed sources, or missed cancellation guarantees exit nonzero. ## Captured baseline findings

See [baseline-summary.json](results/baseline-summary.json) for the cross-report summary and hashes of the immutable source reports. Both complete continuations have `sourceStable: true`; the captured product fingerprints match the initial Chromium report. The initial report itself stopped before its final stability check. These runs used macOS 26.6.2 on Apple M5 Max (18 cores, 128 GiB RAM), Node 22.23.1, and the recorded Playwright browser user agents. Native builds were paused during the timed windows.

| Engine | PDF pages | Total extraction | First indexed page | Foreground read p95 around publication |
| --- | ---: | ---: | ---: | ---: |
| Chromium | 1 | 0.335 s | 305 ms | 21.2 ms |
| Chromium | 100 | 11.740 s | 395 ms | 21.6 ms |
| Chromium | 1,000 | 156.898 s | 778 ms | 35.5 ms |
| WebKit | 1 | 0.170 s | 161 ms | 8.0 ms |
| WebKit | 100 | 4.140 s | 185 ms | 29.0 ms |
| WebKit | 1,000 | 45.468 s | 317 ms | 7.0 ms |

These are separate single-run observations under the launch differences above. The 1,000-page source is 652,935 bytes, with only 157,893 UTF-16 output units total and a maximum of 159 per page. The 31,115,264-byte image PDF was **rejected in both engines** with `CAPACITY: PDF parser requested an oversized range or queue.` It retained an interrupted run with zero completed pages; failure-path elapsed time was 19.782 s in Chromium and 10.367 s in WebKit. Those are rejection timings, not successful extraction performance. Cancellation after the first indexed page drained in 32.2 ms and 10.0 ms respectively, preserving that page and canonical/sync counts.

The Chromium 1,000-page browser descendant RSS peak was 948,864 KiB (approximately 926.6 MiB), from a 388,640 KiB baseline. This includes the entire sampled browser tree and does not imply parser heap growth of that size. **WebKit parser-inclusive RSS is unavailable:** its measured descendant tree contained only the launcher/browser, while WebContent, GPU and Networking XPC services were reparented to PID1. [webkit-process-attribution.json](results/webkit-process-attribution.json) retains a bounded point observation of that topology. The roughly 114 MiB WebKit descendant peaks remain raw evidence, but cannot be compared with Chromium as total extraction memory. The side observation does not guess ownership or sum the other XPC processes.

The strongest next-work evidence is:

1. Resolve the valid image PDF's parser-range incompatibility within the existing source/queue bounds, and remeasure that exact hash. The source-size admission alone does not establish PDF compatibility. Before the rejection, Chromium issued 477 slice and 478 discard requests; their measured request intervals totaled about 9.83 s, indicating substantial transport/checkpoint overhead in the source path, separately from the parser rejection.
2. Profile the page-index credit path: the 1,000-page runs issued 1,000 `advanceExtractionPageIndex` requests totaling 98.35 s in Chromium and 30.13 s in WebKit (roughly 63% and 66% of total extraction time). Publication requests totaled 18.95 s and 4.40 s. This identifies a major wait interval, not isolated FTS CPU; repeated status/maintenance work and durable queue operations must be measured within it before choosing an optimization.
3. Add dense but admitted page/map fixtures and reliable WebKit XPC/heap attribution before making memory or large-document responsiveness claims. Short synthetic pages and descendant RSS cannot close that gate. Preserve first-page credit, exact page publication, canonical immutability, bounded foreground admission and cancellation in any optimization.

## Post-fix capture

[post-fix.json](results/post-fix.json) contains a new, complete ten-case capture: all five cases passed in each engine, with `sourceStable: true`. It uses the SHA-pinned PDF.js bounded-range transport patch (`5de8099723be073084ade9e371597083efa230d74e199c7f5fc1fdd675cf2671` worker; `185a271ba2977f79a23b1223d05d203068bbcc20d10a8ff5c7fd5bbae27098de` patch tool) and the captured targeted page-index credit implementation. The report fingerprints `packages/documents/tooling/pdfjs-range-patch.mjs` in addition to the received parser/build bytes. The exact post-fix harness/comparison sources are retained alongside the report; baseline reports remain unchanged.

```sh
QUIXI_PERF_REPORT=post-fix node perf/documents/run.mjs
node perf/documents/compare.mjs post-fix
```

The comparison tool writes [post-fix-comparison.json](results/post-fix-comparison.json), referencing the full report's SHA-256 and preserving rejected baseline image status. It does not calculate a successful-extraction speed ratio from the image's earlier rejection timing.

| Engine | Case | Baseline total | Post-fix total | Baseline → post-fix index-credit request time | Publication-adjacent foreground p95, baseline → post-fix |
| --- | --- | ---: | ---: | ---: | ---: |
| Chromium | 1 page | 0.335 s | 0.226 s | 0.070 → 0.027 s | 21.2 → 12.1 ms |
| Chromium | 100 pages | 11.740 s | 7.217 s | 6.502 → 3.353 s | 21.6 → 42.4 ms |
| Chromium | 1,000 pages | 156.898 s | 54.943 s | 98.355 → 27.542 s | 35.5 → 16.4 ms |
| WebKit | 1 page | 0.170 s | 0.383 s | 0.014 → 0.049 s | 8.0 → 45.0 ms |
| WebKit | 100 pages | 4.140 s | 6.239 s | 1.913 → 2.252 s | 29.0 → 28.0 ms |
| WebKit | 1,000 pages | 45.468 s | 30.740 s | 30.132 → 11.761 s | 7.0 → 14.0 ms |

The image-heavy original has the **same 31,115,264 bytes/SHA-256 as the rejected baseline** and now completes, publishes and indexes its native-text page: 21.650 s in Chromium and 15.585 s in WebKit. No image decoding/rendering or OCR guarantee follows. First indexed page latency for the 1,000-page text case was 488 ms / 574 ms. Cancellation after index credit drained in 15.7 ms / 17 ms. All cases retained unchanged canonical/sync counts and released both tracked PDF workers.

These are measured results rather than a blanket speedup claim: smaller WebKit cases and several foreground tails were slower. No native build/test ran during the coordinated capture window, but OS one-minute load averages were approximately 9–12 versus approximately 4–7 in the baseline. Chromium's baseline/nonpersistent launch difference remains another confounder. Repeated controlled captures would be needed to assign statistical confidence or isolate causality.

### Residual queue/status observations

The post-fix harness adds a separate window **after** extraction and its success/cancellation checks: two timed public `searchStatus` reads enclosing ten bounded foreground document reads spaced 100 ms apart, plus a count of advisory search-status notifications. The approximately 1.1-second window is excluded from `totalExtractionMs`. It does add real requests, so it is not a measurement of an untouched idle application. RSS sampling now also spans this short post-extraction observation window; memory values must not be compared as identically timed peaks with the earlier capture.

After 1,000 pages, the post-window foreground read p95 was 5.5 ms in Chromium and 21 ms in WebKit; the two full status reads were 15.7/18.6 ms and 12/13 ms. Both snapshots were `ready`, with 1,000 indexed chunks and zero pending sources; neither window received a search-status change notification. This establishes residual request/status cost, **not** that background maintenance ran zero times or consumed that exact latency. Likewise the 1.86 s / 2.36 s of workflow time outside the facade's timed public request intervals includes parser work, untimed chunk reads/ACKs, scheduling and cleanup, and must not be relabeled as idle-maintenance CPU.

The remaining page-credit intervals still totaled 27.54 s / 11.76 s. Private profiling can now distinguish useful index work from residual global status/maintenance scans while retaining the same first-page visibility, foreground bounds and cancellation invariants. This harness cannot supply that internal CPU attribution by itself. Parser-inclusive WebKit RSS remains unavailable because the XPC process topology is unchanged; no memory or complete-plan gate is closed by the post-fix capture.
